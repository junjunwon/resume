서비스 설명

파트너사(사방넷)와 사내 클라이언트가 공유하는 단일 진입점이 없어 인증·트래픽 제어·타임아웃 정책이 서비스마다 흩어질 위험이 있었습니다. Spring Cloud Gateway(WebFlux) 기반 API Gateway를 인증·레이트리밋·라우팅·관측 4개 관심사로 계층 분리해 설계·구현한 프로젝트입니다.

JWT(RS256/JWKS) 인증, 계약 단위 자격증명 인증, 경로 기반 인증 예외 처리, Redis Lua 스크립트 기반 슬라이딩 윈도우 레이트리미터를 자체 설계해 tier별 한도를 분리 적용했습니다.

책임

  • 게이트웨이 패키지 아키텍처 설계 (auth / ratelimit / routing / observability 관심사 분리)
  • 인증 체계 설계·구현 (JWT + JWKS 검증, 계약 단위 자격증명 위임 검증, 인증 결과 캐싱)
  • Redis 기반 분산 레이트리미터 설계·구현 및 tier 정책 수립
  • 장애 격리 정책 설계 (타임아웃 계층, 라우트별 서킷브레이커, 헬스체크 기반 클라이언트 사이드 LB)

주요 기여

  • 레이트리밋 tier 재편 — 기준 자체를 바꿈 — 기존 한도는 엔드포인트 성격 기준(write 100 / read 1,000 req/분)이라 파트너사 한 곳의 트래픽이 다른 계약의 한도를 잠식할 수 있었습니다. 인증 주체 기준으로 재편해 계약 1,200 · 클라이언트 6,000 · 토큰발급 60 req/분 3-tier로 분리하고, 목적을 "쿼터 통제"가 아닌 "어뷰징 차단·blast-radius 제한"으로 재정의
  • 한도 우회 레이스 컨디션 제거 — in-memory 카운터의 check-then-increment 방식은 동시 요청 시 한도를 초과 통과시킬 수 있어, Redis 원자적 Lua 스크립트 기반 슬라이딩 윈도우로 전환해 다중 인스턴스 환경에서도 한도 판정 일관성 확보
  • 토큰 유출 영향 범위 축소 — 공유 bearer 토큰 방식(파트너사 1곳 유출 시 전체 계약 노출)의 취약점을 식별하고 계약코드 스코핑 토큰 구조로 확정해 유출 시 영향 범위를 전체 계약 → 단일 계약으로 한정
  • 인증 비용 제거 + fail-closed 보장 — 요청마다 발생하던 자격증명 해시 검증(약 100ms)을 Caffeine AsyncCache로 흡수해 cache hit 시 인증 오버헤드를 5ms 목표 수준으로 설계. 단일 get(key, loader) 호출로 동시 동일 키 요청의 중복 검증 폭주(stampede)를 차단하고, 예외 시 자동 eviction으로 검증 실패가 통과로 흐르지 않도록 보장 (TTL 60s로 시크릿 폐기 반영 지연 상한 관리)
  • 장애 격리 3중 설계 — Gateway 45s > hub-api 30s > 인증 5s 3단 타임아웃 계층으로 캐스케이드를 차단하고, 라우트 성격별 서킷브레이커 3분류(비즈니스·송장·인증)로 독립 window를 부여해 한 경로의 장애가 다른 경로로 번지지 않도록 blast-radius를 분리
  • XFF 스푸핑 차단 — 프록시 뒤에서 클라이언트 IP를 신뢰하는 방식이 위조에 취약한 문제(CVE-2026-47825 계열)를 확인하고, 신뢰 프록시 hop 수 기반으로 실 출처 IP를 판정하도록 설계. LB 부재로 신뢰 전제가 성립하지 않는 환경에서는 기능 자체를 비활성화하도록 4개 환경(local·dev·staging·prod)별 보안 정책을 분리하고 ADR로 근거 문서화

AI 협업 방식 · 검증

  • 구현·테스트 코드 초안과 영향 범위 탐색은 자체 구축한 에이전트 파이프라인에 위임하고, 인증 스코프·fail-closed 기본값·타임아웃 계층 등 보안 정책 판단은 직접 결정 — 판단 근거는 ADR·스펙 문서로 기록
  • 생성된 코드는 인증 실패 경로·레이트리밋 경계값·fail-closed 동작을 고정한 테스트 228건(테스트 코드량이 운영 코드의 1.7배)을 통과해야만 반영 — "정상 동작"이 아니라 실패 경로가 안전하게 실패하는지를 회귀 기준으로 삼음

서비스 설명

9개 택배사(CJ·롯데·한진·로젠·일양·카카오T·EPOST·딜리래빗·DBOX)마다 응답 포맷과 인증 방식이 달라 표준화가 필요했고, 더 근본적으로는 택배사가 늘어나도 배치 시간이 함께 늘어나지 않는 구조가 필요했습니다.

배송상태를 수집·정제·발행하는 파이프라인 전체를 처음부터 설계·구현했습니다. 어댑터 하나만 추가하면 택배사가 늘어나는 확장성과, 한 택배사의 장애가 나머지 8개로 번지지 않는 격리성을 설계의 기준으로 삼았습니다.

설계 기준

  • 택배사별 수집을 순차로 이어붙이면 택배사가 추가될 때마다 배치 소요 시간이 함께 늘어나므로, 처음부터 동시 실행 구조를 전제로 설계
  • CJ는 건별 조회가 아니라 날짜 기준 대량 처리 방식이라, 처리 특성이 다른 워크로드를 같은 단계에 섞으면 나머지 택배사가 영향을 받음
  • 택배사 API는 통제 밖 의존이므로, 실패를 "막는" 것이 아니라 실패해도 범위가 번지지 않게 가두는 것을 목표로 설정

주요 기여 — 확장성·격리 설계

  • Spring Batch split flow + 전용 TaskExecutor로 7개 택배사 수집 단계를 동시 실행하도록 구성 — 택배사가 추가돼도 배치 소요 시간이 누적되지 않는 구조 확보
  • 스레드 풀 크기를 택배사 수(enum 크기)에 코드 레벨 1:1로 고정해, 택배사 추가 시 설정 누락으로 조용히 순차 처리로 되돌아가는 사고를 원천 차단. 단 상한은 DB 커넥션 풀(HikariCP) 예산으로 제한해 "병렬도만 올리면 커넥션 풀 고갈이라는 2차 병목이 생긴다"는 제약을 근거로 남기고 후속 스케일링 검토로 이관
  • 처리 방식이 다른 CJ 대량 처리를 나머지 7개 택배사와 별도 단계로 격리(bulkhead)하고, 내부는 건별 REQUIRES_NEW 트랜잭션으로 커밋해 한 건의 실패가 전체를 롤백시키지 않도록 분리
  • 재시도 대신 chunk(1) + skip 정책을 채택해 retry storm으로 인한 부하 증폭을 피하고, 택배사별 skip 한도 초과 시 해당 택배사만 실패 처리(나머지 택배사 수집은 계속 진행)
  • 동시 실행 스레드로 넘어가도 로그 상관관계(MDC/trace_id)가 끊기지 않도록 컨텍스트 전파 데코레이터를 적용 — 동시성 도입이 장애 추적 능력을 희생하지 않도록 설계
  • 정규화 계층에 멱등 제약(UNIQUE + 최신 상태만 반영)을 둬 이벤트 도착 순서에 의존하지 않도록 설계. 이 멱등성을 근거로 택배사별 배치 API 호출(단건 N회 → 배치 1회) 등 후속 처리량 개선을 SPIKE/ADR로 설계 검토 완료(구현은 후속 이관)

해결 — 이벤트 아키텍처·정합성

  • 배송상태 변경 판단을 배치 계층에서 먼저 수행해, 변경 없는 송장은 이벤트를 만들지 않도록(Outbox 미생성) 설계 — 무변동 송장 비중만큼 불필요한 발행량을 원천 차단
  • 송장 단위 Transactional Outbox + after-commit 발행으로 "DB 반영 성공 + 이벤트 유실"이 구조적으로 발생할 수 없도록 정합성 보장
  • 택배사 조회 실패(Batch) / 발행 실패(Outbox Publisher) / 소비 실패(DLT)를 장애 도메인별로 분리 격리해 실패 전파 차단

AI 협업 방식 · 검증 — 택배사 9종 Mock 서버 자체 구축

  • 택배사 실계약·실인증키 없이는 9개 연동의 실패 경로·에러 코드를 재현할 방법 자체가 없는 문제를 확인하고, 각사의 wire 프로토콜(인증 방식·채번 규칙·응답 코드 체계·XML/JSON 포맷)을 재현하는 Mock 서버를 구축 — 57개 모듈 / 8,533 LOC / 자체 테스트 255건, 커밋 42/42건(100% 단독)
  • 실 API 명세 채록과 Mock 코드 생성은 AI에 위임하되, 실제와 다르면 검증 인프라 전체가 무의미해지므로 Mock ↔ 실 API 응답 parity를 감사 리포트로 2회 검증해 드리프트를 직접 잡음 — 이 인프라 위에서 9개 어댑터의 정상·실패 경로 반복 검증이 가능해짐
  • 어댑터·파서 구현 초안은 에이전트 파이프라인에 위임하고, 병렬·격리 구조와 트랜잭션 경계·멱등성 설계는 직접 판단 — 산출 코드는 Test-First 게이트(실패 테스트 선행 확인)를 통과해야만 진행

성과

  • 운영 코드 190개 클래스 / 10,311 LOC에 대해 테스트 112개 파일 · 487개 테스트 케이스 확보 — Mock 인프라 덕에 자격증명 발급 대기·택배사 dev 서버 장애 같은 외부 의존 없이 반복 검증. 배송추적 도메인 커밋 116/118건(98%) 수행
  • 9개 택배사를 단일 인터페이스로 통합해 어댑터·파서 추가만으로 신규 택배사 확장 가능한 구조 확보
  • 반품 배송 추적·반송장 획득 등 하위 시나리오까지 동일한 격리·정합성 원칙으로 확장

협업: 백엔드 개발자 3명, 택배사 연동 담당기술 스택: Spring Batch, SpringBoot 4, Java 25, Kafka, MySQL 8, Redis, JUnit, Mockito

3. Kafka 도입 제안 및 배송추적 이벤트 아키텍처 설계

회사: 다우기술대상 서비스: 커머스 택배 허브 (이벤트 플랫폼)아키텍처 / 인프라기여도: 100%

서비스 설명

배송상태 변경을 웹훅 등 하위 시스템으로 안정적으로 전달할 방법이 필요했고, 동기 호출 기반으로는 택배사 API 장애가 파이프라인 전체로 전파되는 문제가 있었습니다. Kafka 도입을 제안하고 이벤트 아키텍처 전체를 설계했습니다.

설계의 출발점은 "Kafka를 어디까지 쓸 것인가"였습니다. 현재 트래픽은 배치 1회당 약 3,000건 · 택배사당 약 2,000건 규모로, 이 구간에서 메시징을 과하게 쓰면 얻는 것보다 운영 포인트만 늘어난다고 판단해 Kafka의 역할을 "비즈니스 이벤트를 전달하는 경계"로 한정했습니다.

설계 판단 — 규모에 맞는 선택

  • 단일 스트림 구조 채택 — 수집 원본을 한 번 흘려보내고 정규화 결과를 다시 흘려보내는 다단 구성도 검토했으나, 현 트래픽에서는 Outbox·발행·소비 지점이 두 배로 늘 뿐이라고 판단. 상태 변경 판단을 배치 안에서 끝내고 확정된 변경만 1회 발행하는 단일 스트림으로 확정 — 운영 포인트를 절반으로 유지하면서 물량이 커지면 파티션·컨슈머 증설만으로 확장 가능한 형태
  • 과설계 판단 후 자체 롤백 — 다건(bulk) 조회 + tasklet 실행 모델을 먼저 시도했으나 실 트래픽 대비 과설계로 판단해 스스로 되돌리고 더 단순한 구조로 회귀. 되돌린 근거를 ADR로 남겨 동일 논의가 반복되지 않도록 정리
  • 발행 게이트를 애플리케이션 비교가 아닌 DB 제약으로 — "이전 상태를 읽어 비교 후 발행"은 동시 실행 시 lost update가 발생할 수 있어, UNIQUE 제약 (송장, 발생시각, 상태)의 INSERT 성공 여부 자체를 발행 조건으로 삼았습니다. 별도 잠금 없이 재조회·재실행에도 중복 발행되지 않는 effect-once 확보
  • self-contained 이벤트 계약 — 수신 측이 DB를 되묻지 않고 이벤트만으로 처리할 수 있도록 이전·현재 상태와 계약 식별자를 payload에 담고, schema_version으로 스키마 진화에 대비. 단 수령자 PII는 이벤트·웹훅 어디에도 싣지 않는 PII-free 투영을 불변식으로 고정

주요 기여 — 정합성·처리량·운영

  • 이벤트 유실이 불가능한 구조 — 배송상태 DB 반영과 Outbox 저장을 동일 트랜잭션으로 묶어(Transactional Outbox) "DB는 반영됐는데 이벤트는 유실"되는 상황을 구조적으로 발생 불가하게 설계
  • 발행 병목 제거 + 무손실 유지 — 발행 스레드가 브로커 ack를 동기 대기하던 구간을 비동기 콜백 마킹으로 정련하고, relay 배치의 재발행 안전망과 수신 측 이벤트 ID 중복 제거를 결합해 at-least-once 발행 + effect-once 처리를 신뢰성 저하 없이 달성
  • hot partition 사전 방지 — 택배사 코드를 파티션 키로 쓰면 물량이 큰 택배사 이벤트가 소수 파티션에 몰려 해당 컨슈머만 밀리는 불균형이 예견됨. 키를 송장 식별자로 확정해 분산을 확보하면서 동일 송장의 순서를 보장하고, "순서 단위 = 키 / 병렬성 단위 = 파티션 수"로 개념을 분리해 물량 증가 시 파티션 수만 독립적으로 늘릴 수 있는 여지를 남김
  • 메시지 유실·poison pill 차단 — Producer acks=all로 브로커 리더 손실 시 유실을 방지하고, Consumer에 ErrorHandlingDeserializer + DLQ를 표준 관례로 도입해 역직렬화 실패 메시지가 컨슈머를 무한 재시도 루프에 빠뜨려 파티션 처리량이 0으로 떨어지는 장애를 차단
  • 장애 도메인 분리 — 택배사 조회 실패(배치) / 발행 실패(Outbox Publisher) / 소비 실패(DLQ) / 웹훅 발송 실패(재시도·이력)를 각각 다른 경계에서 처리하도록 나눠, 한 지점의 실패가 파이프라인 전체를 멈추지 않도록 설계
  • 클러스터 토폴로지 결정 기준 전환 — 트래픽 기준으로 제안된 3노드 Combined 모드(브로커·컨트롤러 겸용)를, Confluent 공식 문서(운영 환경 Combined mode 미지원)와 유사 사내 구축 사례 조사를 근거로 반박하고 브로커 3대 + 컨트롤러 3대 분리(Isolated) 구성으로 전환. 인프라 설치 요청서에 근거 문서로 반영해 운영팀 설득에 사용
  • 로컬 개발환경을 운영과 동일 조건으로 구성 — 공식 권장 dev 최소 구성(3-Combined) 대신 운영과 동일한 6노드 Isolated 토폴로지로 docker-compose 클러스터를 구성해, 컨트롤러 쿼럼·롤링 재시작을 로컬에서부터 운영 조건으로 검증 가능하게 함

AI 협업 방식 · 검증

  • 파티션 키 전략·아웃박스 구현 사례 조사(Confluent 공식 가이드, 업계 실구현 사례)는 AI에 위임하고, 조사 결과를 그대로 수용하지 않고 현행 코드 실측과 대조해 채택 여부를 직접 판단 — 채택·기각 근거를 리서치 문서로 기록
  • 대표 사례: 설계 초안의 "발행 직후 성공 마킹 + try-catch 실패 포착" 모델이 KafkaTemplate 비동기 시맨틱과 충돌(브로커·네트워크 실패는 호출 스레드가 아닌 콜백으로 전달돼 try-catch에 잡히지 않음)함을 검증 단계에서 식별하고, whenComplete 콜백 마킹 + REQUIRES_NEW 트랜잭션으로 정정 — 정정 이력을 문서에 남겨 동일 오류 재발 차단
  • 에이전트가 표면화한 미해결 쟁점(발행 게이트 방식·이벤트 payload 소싱·암호화 범위)은 자율 진행을 차단하고 사람 결정으로만 해소되도록 운영 — 정합성에 영향을 주는 판단 3건을 직접 확정하고 스펙에 결정 근거 기록

성과

  • 택배사 조회 실패·발행 실패·소비 실패를 각각 다른 경계에서 처리하도록 나눠, 한 지점의 실패가 파이프라인 전체를 멈추지 않는 구조 확보
  • 이벤트 유실·중복 발행 두 가지를 코드 규칙이 아닌 DB 제약과 트랜잭션 경계로 차단해, 운영 중 정합성 사고 대응을 사후 검증에서 사전 차단으로 전환
  • 아키텍처 선택·기각 근거를 ADR로 문서화해 이후 스펙-코드 불일치 논쟁을 문서 기준으로 종결

협업: 운영팀, 백엔드 개발자 3명기술 스택: Kafka(KRaft), SpringBoot 4, Java 25, Spring Batch, MySQL 8, Docker Compose

4. Grafana 기반 관측성(모니터링) 체계 설계 및 연동 — 기존 Pinpoint 한계 보완

회사: 다우기술대상 서비스: 커머스 택배 허브 (관측성 인프라)아키텍처 / 인프라 / 운영기여도: 100%

서비스 설명

모니터링 자산이 학습 노트·ADR·docker 스택·게이트웨이 코드에 흩어져 있고, 수집 라인은 컨슈머 Lag만 보는 exporter 1개뿐이었습니다. 알림 규칙은 전무했고, 게이트웨이에 구현해 둔 커스텀 메트릭조차 actuator 노출 설정 때문에 Prometheus로 나가지 않는 상태였습니다.

흩어진 흔적을 하나의 관측성 설계로 통합하고, 사내 표준이던 Pinpoint로는 덮이지 않던 영역을 보완하기 위해 Grafana 기반 3기둥(메트릭·트레이스·로그) 체계를 설계해 실제 연동까지 진행한 프로젝트입니다.

설계 판단

  • 관측성 아키텍처 선정 — 올인원 APM(Pinpoint) 대신 기둥별 best-of-breed 조합(메트릭 Prometheus+Grafana / 트레이스 Tempo / 로그 Loki, 계측 표준은 OpenTelemetry)으로 결론. "Prometheus만으로는 Pinpoint를 대체할 수 없다(메트릭 기둥만 덮는다)"는 점을 명시하고, Pinpoint의 HBase 대비 S3 호환 오브젝트 스토리지만으로 운영 가능한 Tempo·Loki의 운영 비용 이점을 근거로 정리해 도입 문서화
  • 수집 갭 식별 — 기존 kafka-exporter는 Lag·offset 등 프로토콜 레벨 지표만 수집해 JVM GC·힙, 리밸런싱 빈도, ISR 축소(OSR) 전이는 관측 불가함을 확인. 두 exporter를 대체재가 아닌 보완재로 배치하는 구성으로 설계
  • GUI 도구 일원화 — kafka-ui와 AKHQ를 병행 운영하다 기능 중복과 지속적 지표 수집 부적합을 근거로 AKHQ 단일 도구로 통합하고, 상시 관측은 exporter 기반으로 분리

구축·연동

  • 브로커·컨트롤러 6개 노드 전체(100% 커버리지)에 JMX Exporter(javaagent)를 적용하고 MBean 매핑 규칙을 작성, Prometheus 스크레이핑 후 Grafana 대시보드로 클러스터 지표 시각화

문제 정의 (병목 실측)

  • 파일 전체 데이터를 힙에 유지한 채 처리해 60,000건 파일에서 Peak 메모리 1GB+ → OOM — 처리량이 아니라 상주 객체가 원인

판단·설계

  • 생성키 구간과 벌크 구간의 분리 — 주문 생성처럼 생성키(PK) 반환이 필요한 구간과 하위 데이터처럼 벌크 처리가 가능한 구간을 나눠 MyBatis ExecutorType을 SIMPLE / BATCH로 구간별 선택 적용 — "키 반환"과 "배치 효율"의 트레이드오프를 일괄 적용이 아닌 구간 단위로 판단하고, 공용 BatchInsertExecutor로 규격화해 다른 배치에서도 재사용
  • N+1 제거 — 건별 조회를 벌크 조회로 전환해 판매상품 조회 15,000회 → 1회
  • 메모리 상주 제한 — 청크 단위 처리 + 배치 단위 flush·clear 기반 메모리 해제로 힙에 남는 객체를 처리 중 청크로 한정
  • 구조 단순화·실패 격리 — 5개 독립 프로세스를 1개 통합 Job(4단계 Step)으로 재편하고, 파일 단위 독립 처리로 부분 실패 격리, 원자적 상태 변경 Commit으로 중복 처리 배타 제어
